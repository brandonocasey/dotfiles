# Sources for the code-standards rules

The research behind the **Readability** and placement rules in code-quality.md and the comment rules in comments.md. Read it only when asked why a rule exists, or before changing these rules; no rule depends on it. Gathered on 2026-11-06.

## Review and style guides

- [Google: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html). "Too complex" usually means readers cannot understand the code quickly. A good name is long enough to say what the item is or does. Comments explain why code exists; code that cannot explain itself should be made simpler. With no other rule, stay consistent with existing code. "If you can't understand the code, it's very likely that other developers won't either." Backs: the **Readability** intro, naming, matching the code around it, the reread before handoff, and making code clearer before commenting it.
- [Google C++ Style Guide: Goals](https://google.github.io/styleguide/cppguide.html). "Optimize for the reader, not the writer": more time goes to reading code than to writing it. Backs: the **Readability** intro.
- [Google Testing on the Toilet: Write Clean Code to Reduce Cognitive Load](https://testing.googleblog.com/2023/11/write-clean-code-to-reduce-cognitive.html) (Andrew Trenk, 2023). Readers hold about 5–7 items in short-term memory. Keep functions small, hide detail behind abstractions without over-engineering, return early to cut nesting, and minimize mutable state. Backs: one job per function, a flat main path, and explicit data flow.
- [Ellen Spertus: Best practices for writing code comments](https://stackoverflow.blog/2021/12/23/best-practices-for-writing-code-comments/) (Stack Overflow Blog, 2021). Nine rules, including: comments do not excuse unclear code; if you cannot write a clear comment, the code may be the problem; explain unidiomatic code; link copied code and external references; mark incomplete code. Backs: the comment rule on code a reader would misread.

## Books and essays

- John Ousterhout, *A Philosophy of Software Design*, 2nd ed. (2021); [summary of its red flags](https://dev.to/sportebois/software-design-red-flags-wisdom-nuggets-from-john-ousterhout-43i2). Deep modules hide a lot behind a simple interface. Red flags include shallow modules, pass-through methods, conjoined methods, information leakage, vague names, and comments that repeat the code. Backs: keeping defaults and edge cases inside the owning module, extracting only helpers that hide detail, and doc comments for contracts.
- [Ousterhout and Robert C. Martin: APOSD vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code) (2024–2025). Both agree code can be split too finely; Ousterhout argues that entangled methods are harder to read than one undivided method. Both want interface comments on public APIs, and implementation comments only where code is not obvious. Backs: not splitting code a reader must read together, and the doc-comment rule.
- [Sandi Metz: The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction) (2016). Shared code that gains a parameter and a conditional for each new case loops "until code becomes incomprehensible"; "the fastest way forward is back". Backs: extending shared code without a mode flag.
- [Martin Fowler: Flag Argument](https://martinfowler.com/bliki/FlagArgument.html) (2011). A flag argument tells a function to carry out a different operation; Fowler prefers separate methods. Backs: the call-site rule on flags.
- [Refactoring.Guru: Feature Envy](https://refactoring.guru/smells/feature-envy), a smell from Fowler's *Refactoring*. A method that uses another object's data more than its own belongs with that data; "if things change at the same time, you should keep them in the same place". Backs: the owner test and keeping code that changes together in one place.
- [Carson Gross: Locality of Behaviour](https://htmx.org/essays/locality-of-behaviour/) (2020). "The behaviour of a unit of code should be as obvious as possible by looking only at that unit of code." It trades off against DRY and separation of concerns. Backs: placing code next to the code it works with, and keeping a helper beside its only caller.
- Kent Beck, *Tidy First?* (O'Reilly, 2023); [review](https://henrikwarne.com/2024/01/10/tidy-first/). Small tidyings: guard clauses, explaining variables and constants, explicit parameters, reading order, and cohesion order. Backs: a flat main path, named conditions and constants, explicit data flow, and file order.
- [Anthropic: code-simplifier agent](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-simplifier/agents/code-simplifier.md). "Choose clarity over brevity"; avoid nested ternaries and dense one-liners; do not combine too many concerns in one function; follow project standards. Backs: preferring the plain form, one job per function, and matching the code around it.
- [Cursor: deslop skill](https://github.com/cursor/plugins/blob/main/cursor-team-kit/skills/deslop/SKILL.md). AI slop includes comments inconsistent with local style, defensive checks or `try`/`catch` abnormal for trusted paths, casts to `any`, deep nesting, and patterns inconsistent with the file. Backs: no checks or casts for cases the types rule out, and matching the code around it.

## Research studies

- [Gopstein et al.: Atoms of Confusion](https://atomsofconfusion.com/data.html) (FSE 2017). 15 small C patterns caused significantly more misreadings than equivalent plain code (effect sizes 0.22–0.63). They include assignment used as a value, `&&` as control flow, increments inside expressions, the conditional operator, mixed operator precedence, a repurposed variable, and omitted braces. A follow-up found them about once every 23 lines in projects such as the Linux kernel and GCC ([NYU summary](https://cyber.nyu.edu/2018/05/29/prevalence-confusing-code-software-projects/)). Backs: preferring the plain form, and never reusing a variable.
- [Hofmeister, Siegmund, Holt: Shorter Identifier Names Take Longer to Comprehend](https://www.se.cs.uni-saarland.de/publications/docs/HoSeHo17.pdf) (SANER 2017). 72 professional C# developers found defects about 19% faster with full-word names than with single letters or abbreviations ([summary](https://neverworkintheory.org/2021/08/09/abbreviated-vs-full-names.html)). Not all studies agree: [Beniamini et al. (ICPC 2017)](https://www.cse.huji.ac.il/~feit/papers/SingleLetter17ICPC.pdf) found some single-letter names work well. Backs: full-word names, while keeping standard short names.
- [Feitelson et al.: How Developers Choose Names](https://arxiv.org/abs/2103.07487) (IEEE TSE, 2022). Two developers chose the same name with a median probability of 6.9%. Choosing the concepts first, then the words, gave names that judges rated better by about 2 to 1. Backs: naming things in the problem's terms.
- [Arnaoudova: Linguistic antipatterns (thesis)](https://publications.polymtl.ca/1517/1/2014_VeneraArnaoudova.pdf) (2014). Names that contradict behavior, such as a getter that does not return what its name says. In two studies, 69% and 51% of developers judged them poor practice. Backs: a function's name covers everything it does.
- [Muñoz Barón, Wyrich, Wagner: An Empirical Validation of Cognitive Complexity](https://arxiv.org/abs/2007.12520) (ESEM 2020). Across about 24,000 ratings of 427 snippets, Cognitive Complexity, which counts breaks in linear flow and weights nesting, correlated with time to understand code and with rated difficulty; results for correctness were mixed. Backs: a flat main path. The rules set no numeric limit.

## AI-written code

- [CodeRabbit: State of AI vs Human Code Generation](https://coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report). In 470 pull requests (320 AI co-authored, 150 human only), AI pull requests had more than 3 times the readability issues, nearly 2 times the naming inconsistencies, and 2.66 times the formatting problems: 10.83 issues per pull request against 6.45. "AI-produced code often looks consistent but violates local patterns around naming, clarity, and structure." Vendor report; authorship was inferred. Backs: matching the code around it, naming, and the reread before handoff.
- [GitClear: AI Copilot Code Quality 2025](https://www.gitclear.com/ai_assistant_code_quality_2025_research). Moved lines, a proxy for refactoring, fell from 25% of changed lines in 2021 to under 10% in 2024, while copy-pasted lines rose from 8.3% to 12.3%. This tracks the years AI assistants spread; it does not prove who wrote each line. Backs: moving code to the module that owns it, and no duplication.
- [Sonar: The Coding Personalities of Leading LLMs](https://www.sonarsource.com/blog/the-coding-personalities-of-leading-llms/) (2025). Over 4,400 Java assignments, code smells were over 90% of issues for every model tested. Claude Sonnet 4 wrote more than 3 times the lines of OpenCoder-8B for the same problems; Claude 3.7 Sonnet's comment density was 16.4% against GPT-4o's 4.4%. Vendor report. Backs: least code meaning fewer concepts, and the comment rules.
