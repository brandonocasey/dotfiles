## Code comments

- Comment only what the code cannot show: a reason, constraint, workaround, required behavior, or warning about code that deliberately breaks convention. Do not repeat what the code says or describe the change; put the bug, investigation, and ticket in the commit message. Remove redundant comments, and update or remove comments when the code changes. Each comment must make sense to someone who has not read the conversation.
- Comment code a reader would otherwise misread or wrongly change: an order or timing that matters, a workaround, a deliberate break from the usual pattern, where a magic value comes from, what a regex, bit trick, or formula computes, and an invariant callers must keep. When code needs a comment to say what it does, first make it clearer with names and structure; keep the comment for what is still not obvious.
- Write comments in the plain style of [public-writing.md](../../shared/public-writing.md); these rules win where they differ.
- Put the comment at the method or block level, in 1–2 plain sentences a teammate understands on first read. If it must list cases, make the code show them (named constants, a table) and put longer reasoning in the commit message. Doc sections a tool or the repo requires (`# Safety`, `@param`) do not count
- These rules cover doc comments too. Give a new exported item or module a doc comment when its name and types do not show its contract: units, side effects, errors, or valid range. A doc comment states what the item does and its contract in one sentence; link a sibling instead of re-explaining it: `Like [compress], but also accepts empty input.`
- Never write, in code or doc comments: why you added the item or how your caller uses it ("so it can be sent to another thread", "such as when…"); a constant's justification with estimates ("~32 MiB, enough to ride out latency spikes"); earlier behavior ("the old", "previously", "now", "no longer"); or what the signature already shows (owns, borrows, `'static`, `Send`)
- In a repository you do not own (upstream PRs, forks), match its comment density, even where these rules ask for a comment: add no more comment lines per function than nearby code has, and follow its doc style. Put rationale in the PR description, not the code
- Before each commit, list every comment the branch adds, including in new files: diff against the merge-base, not the base tip. Check each against these rules and delete each one a reader would not miss. When unsure whether one helps, delete it, but keep each one the bullet on code a reader would misread requires. Keep directives tools read: shebangs, lint or type pragmas, license headers
- When a reviewer flags one comment, treat it as a sample: reread every comment the whole PR adds, against these rules, and fix all of them before pushing
- State a real requirement with a capitalized RFC 2119 keyword (MUST, SHOULD, MAY, …) https://www.rfc-editor.org/rfc/rfc2119 : `Callers MUST hold the lock`. Lowercase in ordinary prose
- Link external context at the point of use: the source of copied code, the spec tricky logic implements, the issue a workaround works around, and `TODO` plus an issue reference for known-incomplete code
