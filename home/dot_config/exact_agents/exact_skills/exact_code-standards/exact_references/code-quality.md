## Code Quality

- Choose the solution that leaves the least code to maintain within the code the task touches. A larger diff is fine when it leaves less code, such as replacing a copy with a call to a shared helper. Before writing or editing code, prefer in this order: deletion, an existing codebase helper or a method that already sets the same state (call a setter for the initial value instead of repeating its assignments), the standard library, a native platform feature (CSS over JS, a database constraint over application code), an installed dependency, an established package, then minimal new code. Add no interface with one implementation, factory for one product, or configuration for a value that never changes.
- Add a dependency only when it saves significant time or prevents technical debt. Prefer small, well-maintained packages with few transitive dependencies.
- Before changing what code produces or accepts (a return value, output fields, an exit code, an event, a message other code matches, a default, a config key, or a stored or sent data format), list its consumers with `rg` and read each: callers, scripts and agent skills that parse it, copies in other repositories, and older or newer versions that share the data (saved files, caches, pages already loaded, installed clients). Update each consumer in the same change; tests and docs follow the docs rule in Tests & Lint. Where released or already-stored data or an installed client still reads the old form, keep it working, migrate it, or name the break in the PR description. Only in unreleased code with no such data, keep no compat shims, legacy aliases, or deprecation paths unless the user asks.
- Do not edit CHANGELOG files by hand unless the repository documents manual edits; release tooling writes them.
- Fix bugs at the root cause: in the shared code all callers route through, not just the reported path. Check every caller first. Then `rg` the symbol, message, or condition (for added behavior, the handler or flow) for sibling copies that share no code: other commands, handlers, flags, skip modes, overloads, products, platforms, entry points, and fallbacks. When derived objects must carry a flag, policy, or state, find every site that creates one with `rg` before fixing any. Enforce it where they are created rather than with a call at each site; otherwise fix all sites together or list the ones left.
- Before reporting code done, run it on the edge inputs it can meet, not only the happy path: empty, zero, one past each limit (size cap, 255-byte name, exact multiple of a block size); names and paths with Unicode, case, spaces, reserved characters, a repeated basename in another folder, and dots that look like an extension (`v1.2`, `#2.sfc`); sizes or counts read from untrusted data (bound them before allocating).
- For code that creates files, state, locks, or listeners, define what happens on error, cancel, repeat, and concurrent use: remove partial output and reset state on every exit path, guard in-flight work against a second call, and apply a late async result only if it is still current. Cleanup and catch-all handlers never replace or mask the original error; a cancel stays a cancel. Delete only what this operation made or captured, never by shared basename or ID, and keep what another consumer still uses. Exception: code whose job is to prune, sweep, or overwrite data it did not make may act on it only after it shows the data is disposable: another copy exists or nothing else reads it (links, locks, other tools). Age, a missing path, a name match, or a parse that skips unknown fields is not proof. A confirmed run after a preview or dry run (`--yes`) acts only on items the preview listed, never on ones a fresh scan adds.
- When code picks items to show or change (rows, branches, PRs, files, sessions), key the lookup on its full identity (host, repo, owner, branch, project, date, as they apply), not a name, title, suffix, or prefix. Before handoff, list what it must not touch (the same name in another repo or fork, another user's item, another project's rows, an item outside a scope flag such as `--only`) and run each path, fallbacks and early returns included, with one such decoy present.
- For code that aggregates records into a count, total, rate, or cost, or converts between units or scales, work one real sample by hand from the raw input before handoff and compare it to the output. Check unit and scale against the docs and the label, and check each source record counts once: none dropped, none repeated through a copy, replay, fork, nesting, or overlapping list. Label the value by what the code computes.
- For an operation with several side effects (publish then upload, create then configure, back up then migrate, delete then record): validate inputs, config, and preconditions before the first side effect; write each file under a temporary name and rename it into place; write the completion marker only after the last step (a per-item progress record in a loop still follows the loop rule below). Make each step fail in turn, then run the operation again: the rerun finishes or redoes what this operation left half done, and does not repeat a step that already landed (a second post or approval) or stop on what was left (a stale lock, a pending mark, an orphan directory or ref).
- When you add a cache, memo, sent or seen flag, backoff or error record, registry, or listener keyed by an ID, list the events that make it stale (reset, reconnect, resume, a failure, a repeat of the setup that created it, an edit to the inputs behind the key) and clear, rebuild, or remove it at each.
- When one rule lives in two places (native and browser, CLI and UI, Rust and TypeScript, readiness check and real run), change both in one change and test both with the same input. A dry run, preview, or readiness check must call the code the real run calls.
- On a UI thread, main actor, or under a lock, never do blocking I/O, sleep, decode, hash, or a whole-buffer copy per chunk; move it off. In loops over user-sized collections, never scan another collection per item (build a Set or index first), never spawn a process, send a request, allocate, or re-hash per item, and never build one regex or query from all the data. State the expected size and run one case at 10 times it before reporting.
- Never simplify away input validation at trust boundaries, error handling that prevents data loss, security measures, or accessibility basics
- Handle undefined/null where the type system or the callers do not rule it out. Add no null check or `try`/`catch` for a case they do rule out, and no cast to silence a type error. Always include a message when you raise an error
- Type data by its real shape: a named type, not a catch-all like `any`, `Any`, `dict`, or TypeScript `object`. For data of unknown shape, use a checked type (`unknown`) and narrow it
- Before adding a field, option, check, or dependency to existing code, search history for it (`git log -S'<name>' -- <path>`). If an earlier change removed it, read that change and its PR, re-add it only if the reason no longer holds, and say why in the PR description
- Add logs at appropriate levels. Add trace logs only where a failure would otherwise be hard to diagnose
- Export only what a current caller uses. Keep the public API minimal
- In a loop over independent items (repositories, files, worktrees, records), one item's failure warns and the loop goes on. An item that vanished before you acted on it counts as done, not as an error. Record what was done before any step that can fail.
- Keep each failure visible with its cause. Check the exit status or error result of each call whose failure changes the result, and check the result of a call that can report success without doing the work. Do not turn an error into a default, an empty result, or a success, except a fallback the shell-scripts rule (`~/.claude/rules/shell-scripts.md`) asks for, which must warn; keep the cause. A failing optional or best-effort step (a price lookup, a cache, a cosmetic update, a login for an optional feature) warns, and the command still reports its main result and exit code.
- Quote or validate every outside string before it reaches a shell, a git ref, a path join, or a URL. Compare paths as paths, not string prefixes. Decide whether to follow symlinks. Test with a space, a `;`, and a symlink.

## Maintainability

Reviews report breaks of these rules as `requirement` findings.

- No duplication. Before writing a function, block, constant, or style rule, `rg` for code that already does it and call that. When you need a variant, extend the existing code: pass in the part that differs, or split out the shared steps for both callers to use. Do not add a mode flag (see the call-site rule in **Readability**). When the change would otherwise create a second copy, move the logic to the module that owns it and have both callers use it; that edit counts as needed by the task. Leave existing copies the task does not touch. Only copies that cannot share code, such as ones in different languages, are exempt; keep them in sync per the two-places rule above. Client and server code in one language share a module.
- Change only what the task needs. Make no drive-by renames, reformatting, reordering, or refactors in code the task does not need to change. Put an unrelated fix you choose to make in its own commit.
- Put code where it belongs, and choose the place before you write it. Follow the layout the repository uses for that kind of code and any rules it documents. Within that layout, code belongs to the module whose data it reads and changes most, not to the caller you are editing: a tax total belongs with the invoice, not inline in the report renderer. Keep code that changes together in one place, next to the code it works with. Keep a module's defaults, checks, and edge cases inside it, not in each caller. Keep a helper private and beside its only caller; move it to a shared module when a second caller needs it. Code for a concern the current file does not own goes to that concern's module or a new file named for it, never to a generic `utils`, `helpers`, or `common` file when an owning module exists. When the place is unclear, pick the closest match in nearby code and name it in the report. New project, or no repo convention: test files in `test/<type>` (`test/unit`, `test/integration`, `test/fixtures`); built or generated files in subdirectories of `./dist` (`./dist/fe/client`, `./dist/be`, `./dist/coverage`, `./dist/types`).

### Readability

Write for a teammate who knows the language and the repository but not this task. Apply these rules to code the change adds or rewrites. Where the repository's style guide says otherwise, follow it.

- Match the code around it. Before writing in a file, read it and one sibling that does similar work. Reuse their naming, error handling, logging, layout, and idioms, and follow the repository's linter. Bring in a new pattern only when the existing one cannot do the job, and name it in the report.
- Name things for what they are or do in the problem's terms, in full words: `retryDelayMs`, not `d`, `tmp`, or `data2`. A function's name covers everything it does, side effects included: `loadOrCreateConfig`, not `getConfig`, for a function that writes a file. A boolean reads as a yes/no question (`isStale`), and a number with a unit names the unit (`timeoutMs`). Names that fit anything (`data`, `info`, `result`, `obj`, `manager`, `helper`, `utils`, `processData`) are only for short-lived locals. Use one word per concept across the code, not `user`, `account`, and `member` for one thing. Keep the short names the language or repository standardizes (`i`, `err`, `ctx`).
- Give each function one job you can name without "and", with its steps at one level of detail: a function that calls `parseManifest()` and `uploadAssets()` does not also build byte buffers inline. Extract a helper when its name spares the reader its details. Do not extract one that only forwards its arguments, and do not split code a reader must read together, such as steps that pass half-built state back and forth. When the change would give an existing function a second job, restructure it so each part keeps one job; that counts as needed by the task.
- Keep the main path flat. Handle errors and special cases first and return early, instead of nesting the main path in `else` blocks. Name a compound condition (`isExpiredTrial = …`) instead of inlining several `&&` and `||` clauses. Use a lookup table or `switch` over a long `if`/`else if` chain on one value. Do not nest ternaries. Declare each variable in the smallest scope, near its first use, and never reuse one for a second meaning.
- Prefer the plain form to the short one; least code means fewer concepts, not fewer characters. Unless the repository uses the idiom, do not assign or increment inside a condition or argument (`if ((n = read()) > 0)`, `a[i++]`), use `&&` or `||` as an `if` (`ok && save()`), chain assignments, or use `&&` or `and` to make a value conditional (`...(cond ? {x} : {})`, not `...cond && {x}`). Split a dense chain or comprehension into named steps or a loop. Parenthesize mixed `&&` and `||`. Name magic numbers and strings as constants that state the unit or source (`MAX_UPLOAD_BYTES`).
- Make each argument's meaning clear at the call site; `load(url, true, false)` fails this. For booleans and same-typed arguments a caller could swap, use the language's form: labels, keyword arguments, an options object or struct, or an enum. A boolean or mode argument may tune one job (`recursive: true`). It must not switch a function between two jobs, such as `render(items, isPreview)` that runs a different path; split those into two functions that share their common steps. Do not change released public signatures for this.
- Pass what a function needs as arguments and return what it produces. Read environment variables and config at the entry point and pass the values down. When a function changes an argument or shared state, its name says so (`appendRows`, `resetCache`). Give each piece of mutable state one owner.
- In an existing file, follow its order and put new code next to the code it works with, not at the end. Order a new file the way its siblings are ordered; with no sibling, top-down: the entry point or public items first, then the helpers they call, where the language allows.
- Before reporting code done, reread the diff as that teammate. For each new or changed function, say in one sentence what it does from its name and signature alone. Then read its body top to bottom without opening other code to learn what a name means. Fix each failure in code the change added or rewrote: rename, restructure, or comment it per comments.md.

## Edge cases to list before coding

Before writing code in these areas, list the cases below that apply. Handle each one or name why it cannot occur. Add a test for each case the code handles with its own branch; cases one path handles alike share one table-driven test.

- **Code that runs git against user repositories, or deletes, moves, or restores user files:** submodules (uninitialized, nested, with local-only refs), nested untracked repos, sparse checkouts, skip-worktree and assume-unchanged files, ignored files, staged changes that differ from the tree (including staged deletions, renames, and type changes such as a symlink replaced by a file), unborn and detached HEAD, missing, prunable, or locked linked worktrees, and user git config that changes defaults (`merge.autoStash`, `status.showUntrackedFiles`). Parse paths and names from git output with `-z` (NUL-separated), never by splitting on whitespace or newlines.
- **Replacing, matching, or branching on the output, state, or config of another tool or host (gh, glab, git, a script, a web API):** first write a table of its behavior for each flag, edge input, and variant the code can meet: each status code, exit code, and message form its docs or source define (not one observed sample), each forge and self-hosted host, fork, a commit that only a tag or a remote branch holds, and the order in which the tool reads config and environment. Read its source or docs, or run it. Test each row the code treats differently; rows it treats alike need only one case. Report each deliberate difference.
- **Async UI, polling, event handlers, or code that orders, merges, or compares by time:** two actions in quick succession, responses out of order, a failed or slow request, a record read while half written, user input that a refresh would discard, two events with the same timestamp, `<` against `<=` at each boundary, an event just before a deadline, a timestamp that later edits overwrite, and list order that differs from history order.
- **Scripts that run on pages you do not control (embed, registry, page-scan, or watcher code):** applies when the change touches startup, page scan, div claim, observers, shared window state, or per-div data lookup. The script runs twice or in two copies. It starts before DOMContentLoaded, between it and load, and after load. A div is added late, removed, or replaced by one with the same id while an embed is in flight. Two divs share an id, or a div that already has a player is embedded again. Two sites or libraries share the page, loaded in either order, and one player has no pid. A second run reuses, replaces, or tears down the first run's state. Instance 2..N resolves data with the same precedence as instance 1: test an attribute set only on div 1 and a key set on both.
