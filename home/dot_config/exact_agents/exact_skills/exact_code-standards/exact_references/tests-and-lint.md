## Tests & Lint

- Run checks relevant to the change and all checks the repository requires. Fix failures the change caused.
  For other failures, establish their cause and effect on validation, and report them with evidence.
  Fix them only when they block the requested work and are in scope; otherwise ask.
  After a fix, rerun affected checks; broaden only for a new change, failure, or unresolved concern.
- For a bug fix, write or find a test that reproduces it through the real entry point with the real input shape; for an error, use the message production code builds, not a hand-written one. Run it before the fix and show that it fails. After the fix, show that it passes, and run the existing suite. Revert only the fix and confirm the test fails for the reported reason, then restore it. Never edit, skip, or special-case the reproducing test after writing it. A test that calls a helper directly does not cover the code that wires it in: remove the wiring in a scratch change, confirm a test fails, and restore it. If no test can reproduce the bug, show a manual reproduction before and after; for UI, follow `ux-verify`.
- New behavior needs the same revert proof as a bug fix: for each guard, skip, or branch it adds that callers can see, delete or invert it in a scratch change, confirm a named test fails, and restore it. A branch no caller can observe (logging, metrics, a cache or speedup that returns the same result) needs no test; list it in the report. Use input that makes the branch matter (absent, null, duplicate, reordered). A test proves nothing if it also passes on base, takes another route than real input (zipped instead of loose, only the first event), or uses a mock that makes the branch moot. Each test you add must fail on at least one scratch break: one of these reverts, its wiring removed, a changed result in new code with no branch, or base for a bug fix. Do not keep one that fails on none, unless it pins existing behavior before a refactor. Report each revert and wiring check as `<scratch change> → <failing test>`.
- Add a test only when it can fail for a defect that matters to a caller (a wrong result, lost or leaked data, a hang, a crash) and that the existing tests miss. Name that defect before you write the test; if you cannot, write none. Do not test what the compiler, type checker, framework, or a dependency guarantees (lifetimes, ownership, `Send`); values copied from the code (constants, log text) that no caller reads; or a thin wrapper whose wrapped path a test already covers. This bullet and the next win over the per-case and per-row test lines in **Edge cases to list before coding**.
- Test behavior, not structure. Call what callers call (a public function, command, endpoint, or page), not a private helper. Assert the result or state, not which calls ran, unless the call is the behavior (a sent message, a request, a read that a cache avoids). A refactor that keeps behavior must not break the test. Take expected values from the spec, docs, or an example you checked by hand, never by calling the code under test or a copy of its logic. Use real code and local tools (temp git repo, temp files); fake only what is slow, nondeterministic, or remote (network, clock, other services), never the code under test. Test each behavior once for each code path that implements it: put its other inputs in the same table-driven test, one per input class or boundary.
- After fixing a finding or failure, check the fix as new code: run the root-cause sibling search and the edge, failure, two-places, and 10x-size checks of the **Code Quality** section on it. Read the documented contract of each format, message, check order, or default it changes, and confirm library or tool behavior in docs, source, or a probe. Rerun the failing case and cases that passed before the fix: default or empty state, missing input, and a second run.
- When you write or change a lint rule, CI gate, test harness, scorer, or verification script, inspect the inputs it reads and show it fails on a known-bad case before trusting its pass. Make the bad case in a scratch copy, a temporary input, or a reverted change, and remove it afterward.
- Before reporting a check or measurement, confirm from its output that it ran on the current change, not cached, skipped, or stale. When a result beats the expectation you held beforehand, find the cause before reporting it. Rerun only to settle that doubt.
- Make tests use a temporary HOME, XDG_* directories, database, and git repository. Tests never touch the user's real config, logs, or data. Put directories that you make by hand under the AGENTS.md scratch path.
- Give long tests, builds, and background runs a task-appropriate timeout. If output stops, inspect process activity and available progress indicators. Stop only when the timeout expires or evidence shows a hang. Isolate the failing test when identifiable.
- When a change alters behavior, a command, a flag, a config key, or a default, update its tests and docs in the same change. Docs include README, `docs/`, man pages, shell completions, help text, and config schemas. If docs are generated, change the source and run the generator; never edit the generated output. Before committing, `rg` the whole repository for every changed or removed flag, command, path, message, and behavior claim. Include skills, AGENTS.md, comments, and error hints that name a flag. Fix each stale mention. In the final report, list the updated docs or write "Docs: none affected".
- Check each factual claim in a comment, doc, help text, or PR description (what other code does, counts, names, limits) against the final code. After the last edit or push, reread every one you wrote and `rg` the old value (count, label, message, each locale) in tests and docs.
