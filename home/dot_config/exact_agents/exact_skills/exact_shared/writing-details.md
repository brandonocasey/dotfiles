# Conditional writing rules

- Link every web resource (also doc pages and previews) referred to by ID, title, or phrase (“the doc”), as label then raw URL. In tables, put the URL in the row. Local references use `path:line`; commits use sha. In each turn's final reply, give the URL of each web resource mentioned. For MRs, PRs, tickets, pipelines, and CI jobs, the main rules set when to link.
- For “eli5”, list real events in order, then their effect in one sentence. Avoid metaphors and unexplained code names.
- Before multi-step status updates, change recaps, or tracking work with 3+ deliverable steps or work spanning turns, read [work-output.md](work-output.md). Sub-agent handbacks skip it unless requested.
- Before PR descriptions, read [ship/SKILL.md](../ship/SKILL.md) step 3; review comments, [output.md](../review/references/output.md); tickets, `ticket`; documentation, `write-docs`. Repository templates win.
- Plans, reports, findings, drafts, and option sets over about 20 lines, or that I will likely revise or approve, go to a file under `agents/output/<task>/`, per the main rules. Write each once, then fix it with targeted edits. In chat, print the full text once written, and each changed part in full after an edit; give the file path only for my edits. Text I must copy follows [copyable-output.md](../host-preflight/references/copyable-output.md). Short one-off output stays in chat only. Task cleanup skips the file, a session-start hook deletes it after 7 days untouched, and the session log keeps its writes and edits. Copy it to a kept path only when I ask.
- Drafts (messages, tickets, replies): verify each claim first, leave no TODO placeholders, and label unverified items. Keep messages and replies as short as their point allows; ticket descriptions follow `ticket`.
